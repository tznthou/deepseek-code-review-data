# D：規範另外用一次呼叫（2026-09-26 子超選定，compact 後執行）

## 假設（還沒驗證的推論）

v01 的功能性掉了 3.6pp（holdout 盲標），推測是同一次呼叫裡規範分走了注意力。
分成兩次呼叫：一般 review 完全不動（= v00），另外一次只看規範，兩邊 finding 合併。
推論成立的話，功能性保得住，規則類的提升也拿得到。

## 設計

- **一般 pass**：kit 現況（v00）。直接用 Qodo 既有的 base-1、base-2，不用重跑
- **規範 pass**：system prompt 照舊用 kit 的 rubric（輸出格式相同、吃得到快取）；
  user message = PR 資訊 + diff + 規範（v01 的呈現：after_diff／full／list／h1）+ 一句任務範圍說明
  - 範圍說明要寫成「任務範圍」，不是「自我約束」。例：「這一次只檢查上面這些規範有沒有被違反；一般的程式問題由另一次 review 處理」
  - ⚠️ 措辭如果要改，在調參組試，不在 holdout 試（holdout 只做確認）
- **合併**：兩個 pass 的 finding 直接串起來，先不去重；另外記重複數（同檔、行號 ±3、講同一件事）
- **實作**：本目錄新增 scripts；不要動 loop 已凍結的 Guard targets（`render.py`、`review_with_rules.py` 等，見 `guard-targets.sha256`）

## D0f 同位置的 finding：重複還是不同問題（2026-09-26，`scripts/d0f_colocated.py` → `d0f-colocated.md`，判讀 `d0f-colocated-judgments.csv`）

15 組（兩輪 9＋6）：**9 組重複、6 組不同問題**。
- 重複的 9 組盲標就判得出來（兩邊都跟同一則標準答案 same），逐組讀過也成立：print、console.log、strict、namespace、include guard 這類。
  一般 pass 早就抓到了，只是沒標規則；規範 pass 在這裡多給的只有「違反哪一條」。其中兩組一般 pass 的信心只有 0.5／0.6，規範 pass 是 0.95／0.99
- 不同問題的 6 組裡，**4 組是規範 pass 在同一處抓到一般 pass 沒講的違規**：cal.com-11 直接讀 process.env（×2，一般 pass 講的是變數名稱可能撞到既有設定）、
  redis-3 malloc 改 zmalloc（×2，一般 pass 講的是 off-by-one 與 NULL 檢查）
- 另 2 組（tauri-2，都只在第一輪）是規範 pass 的雜訊，信心都 0.6：一則缺文件註解（不在標準答案），一則自相矛盾（標題說用了 expect，內文承認沒用）。過濾只看「有沒有標有效編號」，擋不住這種

對正式功能的意思：
- **照位置直接丟掉規範 pass 那則，丟錯邊**：規則類同一問題兩輪合計 28 → 25（v00 是 13，收穫保住 80%），掉的正是上面那 4 組新抓到的；
  而重複的那 9 組，留下的反而是沒標規則、信心較低的那則
- 不去重：每 PR 約多 0.15 則重複留言（每輪約 4.5 則／31 PR）
- 較好的形狀是**同位置合併成一則**（兩邊的重點都列、標出規則），不丟任何一邊；要看 post 階段怎麼貼行內留言才知道好不好做
- 規範 pass 另設信心下限（例如 ≥0.7）也許擋得掉 tauri-2 那種雜訊，但會不會誤殺真的違規還沒算（$0 可算）

## 規範 pass 要不要另設信心下限（2026-09-26，`scripts/d0f_conf_floor.py`、`show_findings.py`，判讀 `d0f-lowconf-judgments.csv`）

kit 現況：摘要列出全部 finding；行內留言只貼「嚴重度 ≥ minor 且信心 ≥ 0.7」（`post_review.py`，每 PR 最多 8 則）。
所以信心 < 0.7 的規範 finding 本來就不會變成行內留言，下限只決定它們要不要連摘要都不列。

低於 0.7 的規範 finding，兩個切分共 12 則（holdout 5、調參組 7），逐則對照 diff 與規則原文：

| 判讀 | 則數 | 例 |
|---|---|---|
| 真的違規（盲標 same 或引用命中） | 4 | 沒用 thiserror、logger 初始化、檔尾缺換行、不必要的註解 |
| 真的違規，但不在標準答案 | 1 | 行尾多餘空白（Biome 會清掉） |
| 相關但不同（盲標 partial） | 1 | dify-10 的 `__str__`：GT 是缺對應的 `__repr__` |
| 有爭議 | 1 | prefect-9 沒附測試檔：R10 字面要同目錄有測試檔，規則目的講的是位置 |
| 誤報 | 5 | 私有函式說成 pub、上方就有 `///` 卻說缺文件（×2）、沒用 expect 卻說用了、change file 格式其實是 repo 慣例 |

- **設 0.7 下限會誤殺**：砍掉 5 則誤報，同時砍掉 5 則真的違規（另 2 則部分相關／有爭議）。在 0.5–0.6 這一帶，信心分不出真假
- 合併後規則類同一問題（holdout 盲標）兩輪合計 28 → 27；調參組規範 pass 抓到的規則類 GT 73 → 70（引用命中）
- 不設下限的代價只是摘要多幾行：12 則分散在 100 PR × 2 輪，而且都不會變成行內留言
- 結論：**不另設下限**，沿用 kit 的行內門檻（放行的真違規 holdout 24/27、調參組 70/73，其餘留在摘要）。
  做同位置合併時，只合併本身過得了行內門檻的規範 finding；否則 tauri-2 那種低信心誤報會搭著一般 pass 的行內留言貼出去
- 5 則誤報都是「講的事 diff 直接就能反駁」（pub、`///`、expect、格式），跟待辦 ③「claim 型 grep 反駁」同型；樣本只有 5 則，射程要另外算

## 正式功能：post 階段做同位置合併好不好做（2026-09-26 讀 code，`scripts/colocation_eligible.py`）

post 階段現況（`reusable-ai-review-post.yml`；repo 自己的 04 也是 `uses:` 它 `@v1`，只有一個入口）：
`deepseek_review.py` → `review.md`（摘要：判定、表格、details、token 頁尾）＋ `findings.json`（行號已先定位）→
`post_review.py`：過濾（嚴重度 ≥ minor、信心 ≥ 0.7、定位得到、行號在 diff 可留言範圍內）→ 取前 8 則 →
摘要用 `gh pr review --comment` 貼（每次 push 新建一則）→ 行內逐則 POST，已有同 `(path, line)` 的跳過（跨 run 的冪等）。

**合併本身好做**：放在 `post_review.py` 過濾之後、取前 8 則之前最自然，那裡只剩過得了門檻的 finding，行號也是最終的。
同一處（同檔、±3 行）的一般＋規範 finding 組成一則留言，`post_inline` 收一個合成的 finding 就能貼，約幾十行。

射程（只算過得了行內門檻的）：

| | 行內留言（兩輪） | 同一處 ≥2 則 |
|---|---|---|
| v00 單一 pass（100 PR） | 249／254 | 8／14 組（8／12 個 PR） |
| D0f 跨 pass（holdout 31 PR） | 92／99 | 跨 pass 6／5 組 |

- **只合併跨 pass 的組**：沒設規範檔的使用者行為完全不變（`@v1` 是浮動 tag，這條要守住）。D0f 每輪少 5～6 則留言
- 通用合併（連單一 pass 自己的同位置也併）會改到所有使用者：100 PR 裡 8～12 個 PR 的留言數會變，要當行為變更另外評估
- 超過 8 則上限的 PR 每輪 1 個，合併前後一樣，上限不是問題

比合併難的是周邊：
1. **摘要**：規範那次呼叫自己的 review.md 列的是全部 finding（沒過濾），不能直接接上去；要用過濾後的 finding 另外渲染一段
2. **第二次呼叫失敗要隔離**：loop 的 v03b 就遇過一次 JSON 解析失敗；規範那次壞掉時一般 review 照樣要貼
3. **跨 run 冪等是「同 (path, line) 就跳過」**：第二次 push 時，規範 finding 若落在上一輪一般 pass 留過言的行，整則會被跳過，只剩摘要看得到。這是現有語意，不是新 bug，但要寫進文件
4. **驗證不能靠自家 PR 的 CI**：04 釘 `@v1`，改 post_review.py 的 PR 跑的是已發布舊版；要用 `post_review.py --dry-run` 餵合成 finding，並加 selftest
5. **規範檔格式**：Qodo 的規範是結構化條目，真實 repo 多是 AGENTS.md 這類自由文字；R01… 的編號要先定格式
6. **外送安全**：規範檔要送給 DeepSeek，觸發 09-22 的重開條件，採用前先裁定

順帶：`post_review.py` 開頭 docstring 說摘要用 `gh pr comment --edit-last --create-if-none`（冪等），實際 code 從搬到現在路徑那天起就是 `gh pr review --comment`（每次新建）。行為符合當初的取捨（memory pr-comment-idempotency-tradeoff），錯的是註解。
